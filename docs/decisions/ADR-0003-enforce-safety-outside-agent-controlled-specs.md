# Enforce safety outside agent-controlled specs

## Context and Problem Statement

During the grocery-planning stress test, the design added `side_effects` to tool operations to describe irreversible or costly actions. That immediately exposed a flaw: if agents can generate their own specs, they can also omit or mislabel the very fields meant to constrain them. We needed a safety mechanism that still works when specs are generated by the model itself.

## Decision Drivers

* Keep enforcement in a layer the agent cannot modify or rely on self-reporting to satisfy
* Preserve useful consequence information for the model without conflating hints and policy
* Allow zero-config or agent-generated tool integrations without making them fully trusted by default
* Support user-controlled approval gates, restrictions, and auditability across primitives

## Considered Options

* Keep `side_effects` as a hint and enforce safety through a separate Policy Layer plus a spec trust model
* Use `side_effects` as the enforcement source for approvals and dangerous operations
* Disallow agent-generated specs entirely and require all tools to be human-authored and pre-approved

## Decision Outcome

Chosen option: "Keep `side_effects` as a hint and enforce safety through a separate Policy Layer plus a spec trust model", because enforcement must live outside agent-controlled artifacts while still allowing the model to reason about consequences and draft new integrations.

### Consequences

* Good, because the runtime can block or gate actions even when the model misbehaves or generates a misleading spec.
* Good, because users can define domain allowlists, file restrictions, approval rules, and primitive restrictions independently of tool authors.
* Good, because agent-generated specs remain possible through an untrusted-to-reviewed-to-trusted progression.
* Bad, because the runtime becomes more complex and must evaluate policy consistently at creation time and execution time.
* Bad, because `side_effects` can no longer be treated as authoritative enforcement metadata, which may surprise readers who expect policy to be spec-local.

### Confirmation

This decision is confirmed if mutating or dangerous operations can be gated even when a spec omits `side_effects`, and if untrusted specs receive stricter handling automatically. `docs/architecture.md` should continue to describe the Policy Layer and spec trust model, while `docs/tool-spec-format.md` should keep `side_effects` framed as informational rather than authoritative.

## Pros and Cons of the Options

### Keep `side_effects` as a hint and enforce safety through a separate Policy Layer plus a spec trust model

This is the chosen defense-in-depth model.

* Good, because it separates model guidance from runtime enforcement.
* Good, because it supports trusted and untrusted specs without changing the primitive set.
* Neutral, because well-authored specs still improve behavior even though they do not control permissions.
* Bad, because safety logic now spans policy configuration, trust evaluation, and primitive middleware.

### Use `side_effects` as the enforcement source for approvals and dangerous operations

This keeps enforcement close to the tool definition.

* Good, because the design appears simpler and more local to the spec.
* Neutral, because it works if every spec is accurate and trustworthy.
* Bad, because self-reported safety data is untrustworthy when the agent can author or modify specs.
* Bad, because enforcement becomes fragile precisely in the cases where safety matters most.

### Disallow agent-generated specs entirely and require all tools to be human-authored and pre-approved

This maximizes strict control.

* Good, because the runtime only executes reviewed interfaces.
* Good, because it simplifies trust handling.
* Bad, because it gives up one of the most compelling parts of the architecture: zero-config tool adoption from documentation.
* Bad, because it forces every integration through a manual bottleneck.
